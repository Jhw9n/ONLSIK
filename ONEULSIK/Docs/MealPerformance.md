# 식품 검색 및 AI 식사 분석 성능 (#19)

## 1차 적용 범위

- 일반 식품 검색의 결과·순서·중복 선택 정책·영양값·DB 파일은 변경하지 않았습니다.
- 대표 음식은 식품코드 기본키로 먼저 조회합니다. 원본 이름·단위·출처·날짜·분류, 영양값 유효성 및 입력 단위 호환성을 확인합니다. 브랜드나 추가 설명이 있으면 생략합니다. 조회 결과가 없거나 조건이 맞지 않으면 기존 검색으로 돌아갑니다. DB 오류를 임의 음식으로 대체하지 않습니다.
- actor 안에서 읽기 전용 SQLite 연결을 재사용하고 연결 소유 객체가 해제될 때 닫습니다. statement는 각 쿼리 종료 시 정리합니다. actor에서 조회와 캐시를 직렬화합니다.
- 검색 결과와 식품코드 조회 결과를 합쳐 최대 64개 키의 LRU 메모리 캐시를 유지합니다. 일반 검색은 최대 100개 결과를 저장합니다. 검색 키의 내부 공백을 없애지 않아 `참치 김밥`, `김밥참치` 등 서로 다른 조건을 잘못 합치지 않습니다. 빈 결과도 캐시하지만 오류·취소 결과는 저장하지 않습니다.
- 캐시는 현재 실행 중인 번들 DB에만 유효하며 앱 재실행 시 새로 만들어집니다. 향후 실행 중 DB 교체 기능을 도입하면 연결과 캐시를 함께 초기화해야 합니다.
- FTS5, DB 재생성·정규화 변경, LLM 묶음 판정, 추정값 캐싱은 이번 범위에 포함하지 않습니다. 미등록 음식의 첫 부분 검색은 기존 전체 검색 비용이 남습니다.

## 측정 로그

Debug 빌드에서 Console의 `MealPerformance` 카테고리로 확인합니다. `analyze`와 후속 답변 `clarify`마다 서로 다른 trace ID를 부여합니다. 전체 시간, 실제 LLM 응답 요청 수와 시간, DB 검색/직접 조회 시간, 실제 쿼리·연결 열기·캐시 적중 횟수를 기록합니다. 모델 내부 토큰 처리 횟수가 아닌 앱에서 `respond`를 호출한 횟수입니다.

- `llm.extract`, `llm.assess`, `llm.rewrite`, `llm.portion`, `llm.nutrition`: 실제 모델 요청만 측정하며 분량 재시도와 영양 추정 후 별도 분량 호출도 각각 집계합니다.
- `db.search`, `db.lookup`: actor 대기 시간을 포함한 호출 경과 시간입니다.
- `db.query`, `db.open`, `db.cacheHit`: 내부 진단용입니다. 이 시간들을 상위 DB 시간과 다시 합산하지 않습니다.
- `completed=false`: 오류나 취소로 반환하지 못한 요청입니다. 확인 질문으로 정상 반환된 경우에는 `true`입니다.

사용자 문장·음식명·영양값·사용자 ID는 앱 성능 로그에 넣지 않습니다. Trace의 집계는 lock으로 보호하며 요청별 TaskLocal을 통해 DB actor에 전달됩니다. Release 빌드에서는 Trace 생성 및 로그 출력을 생략합니다. CLI에서만 `ONEULSIK_METRICS_STDOUT=1`을 설정하면 동일 요약을 표준 출력으로도 확인할 수 있습니다.

## 재현

Xcode와 해당 Swift SDK가 있는 Mac에서 프로젝트 폴더 기준으로 실행합니다.

```sh
bash Scripts/benchmark_meal_entry.sh
bash Scripts/benchmark_meal_entry.sh --compare /이전/측정폴더/search.json
bash Scripts/benchmark_meal_entry.sh --live
```

첫 명령은 96개 검색 케이스를 각각 세 번 조회하고 임시 폴더에 순서·ID·영양값·출처 등을 포함한 `search.json`을 저장합니다. 두 번째는 이전 결과와 동일한지 검사합니다. 검색 결과가 없거나 한국어 검색어가 짧은 경우도 포함합니다. 세 번째는 Apple Intelligence가 실제로 사용 가능한 Mac에서 1·3·8개 음식의 분석을 수행합니다. 벤치마크용 고정 입력이며 식사 기록은 저장하지 않습니다. 임시 폴더에는 실행 파일과 약 92MB DB 사본이 남으므로 결과 보관 후 해당 폴더를 정리할 수 있습니다.

비교 실행 시 모델 워밍업, 캐시 상태, 발열, OS와 기기 차이에 주의합니다. 각 검색 케이스의 첫 조회도 앞선 케이스나 OS 파일 캐시의 영향을 받을 수 있어 완전한 cold-start 측정이 아닙니다. 실제 사용자 속도 보장은 아닙니다.

## 2026-11-04 측정

arm64 Mac, macOS 27.0.1, Swift `-O -D DEBUG`, 동일 번들 DB로 측정했습니다. 개선 전 코드는 main `c80a4bf`에 동일한 측정 로그만 추가한 상태입니다.

| 항목 | 개선 전 | 개선 후 |
|---|---:|---:|
| 검색 케이스 첫 조회 중앙값 | 205.90ms | 162.20ms |
| 같은 검색 반복 중앙값 | 206.44ms | 0.022ms |
| 음식 1개: DB / 전체 | 111ms / 7,518ms | 1ms / 3,935ms |
| 음식 3개: DB / 전체 | 347ms / 2,198ms | 1ms 미만 / 1,570ms |
| 음식 8개: DB / 전체 | 1,341ms / 4,723ms | 1ms / 3,290ms |

전체 분석은 케이스별 1회 측정입니다. 특히 첫 음식은 모델 초기 준비 시간이 달라 전체 단축분을 DB 개선 효과라고 단정할 수 없습니다. 이번 고정 입력에서는 전후 모두 LLM 추출 1회만 필요했고, 대표 음식 연결·분량이 같아 후보 판정 호출 자체가 없었습니다. 애매한 음식의 다중 LLM 호출 성능은 별도 측정이 필요합니다.

96개 검색의 결과 순서·영양값·출처가 모두 같았고, 실제 모델 1·3·8개 분석의 식품코드·수량·분량·열량도 동일했습니다. 기본키 조회 계획은 `sqlite_autoindex_foods_1` 사용을 확인했습니다. 앱의 시뮬레이터 대상 Debug 빌드도 통과했습니다.

## 실기기 확인

1. 앱을 새로 실행해 `김밥 한 줄`을 입력합니다.
2. `김밥 한 줄, 쌀밥 한 공기, 미소된장국 한 그릇`을 입력합니다.
3. 같은 문장을 다시 입력하고 결과와 대기 시간을 비교합니다.
4. 실제 먹은 복합 메뉴도 시험해 불필요한 질문·분량 변화·지연 여부를 확인합니다.

체감이 느리면 문장과 대략적인 대기 시간, 가능하면 해당 `MealPerformance` 로그를 함께 확인합니다. 일반 검색이나 추정 실패가 필요한 음식은 대표 음식보다 여전히 오래 걸릴 수 있습니다.
