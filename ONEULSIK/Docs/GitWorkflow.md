# Git 및 GitHub 작업 규칙

## 1. 적용 범위와 권한

오늘식(ONEULSIK)의 이슈, 브랜치, 커밋, 푸시, PR 작성 규칙이다.
이 문서는 작업 기준이며 GitHub 인증이나 실행 권한을 대신하지 않는다.

- 사용자가 “이 작업은 이슈 생성부터 초안 PR까지 진행해줘”처럼 전체 흐름을 맡기면
  아래 절차를 중간 재확인 없이 진행한다. 도구의 권한 승인 절차는 그대로 따른다.
- 구현만 요청한 경우에는 구현과 검증까지만 진행한다.
- 커밋, 푸시, PR 중 일부만 요청한 경우에는 요청한 범위만 진행한다.
- PR은 기본적으로 초안으로 생성하고, 머지는 사용자가 검토한 뒤 별도로 요청할 때만 진행한다.
- 현재 작업과 관계없는 이슈 생성, 변경 포함, 파일 정리 등은 하지 않는다.

## 2. 작업 전 확인

1. `git rev-parse --show-toplevel`로 저장소 루트를 확인한다.
2. 현재 브랜치, 작업 트리 변경, 원격 저장소와 추적 브랜치를 확인한다.
3. 저장소 루트의 `.github/ISSUE_TEMPLATE/` 및 `.github/PULL_REQUEST_TEMPLATE.md`를 확인한다.
4. GitHub CLI를 쓰는 경우 인증 상태를 확인하고, 확인한 원격 저장소를 명시해 작업한다.
5. 사용자가 이슈 번호를 지정했다면 해당 이슈를 읽는다. 지정하지 않았다면 기존 이슈를 검색한다.

앱 폴더와 Git 저장소 루트가 다를 수 있다. 템플릿 경로는 저장소 루트를 기준으로 찾고,
GitHub 저장소 이름이나 기본 브랜치를 폴더 이름만으로 추측하지 않는다.

## 3. 이슈

### 제목

`[유형] 작업 목적`

| 유형 | 용도 |
| --- | --- |
| feat | 새로운 기능 추가 |
| fix | 오류 수정 및 기존 동작 개선 |
| perf | 성능 개선 |
| refactor | 동작을 유지하는 내부 구조 개선 |
| test | 테스트 추가·수정 및 검증 체계 구축 |
| docs | 문서 작성·수정 |
| chore | 설정·의존성·개발 환경 정리 |

예: `[fix] AI 식사 기록 실사용 검증 및 오류 개선`

실사용 테스트 과정에서 앱 동작을 수정하는 작업은 `fix`로 분류한다.
테스트 코드나 검증 체계 자체가 주된 결과물일 때 `test`를 사용한다.
같은 문제를 다루는 열린 이슈가 있으면 재사용한다. 범위가 다른 작업은 별도 이슈로 분리한다.
기존 이슈의 제목이나 범위를 크게 바꾸려면 사용자에게 확인한다.

### 본문

기존 이슈 템플릿의 제목을 유지한다.

```markdown
## 🔥 Issue 내용
현재 문제, 작업 목적, 변경 범위와 제외 범위를 설명한다.

## ✅ To-do
- [ ] 필요한 작업
- [ ] 관련 검증
```

존재하지 않는 라벨이나 담당자를 임의로 지정하지 않는다.

## 4. 브랜치

- 이름: `유형/#이슈번호`
- 예: `feat/#17`, `perf/#19`, `fix/#21`, `docs/#번호`
- 이슈 제목 전체를 브랜치명으로 쓰지 않고 유형과 이슈 번호로 연결한다.
- 같은 이슈의 적절한 작업 브랜치가 있으면 재사용한다.
- 기본 시작점은 최신 원격 `main`이다. 실제 기본 브랜치가 다르면 확인한 기본 브랜치를 사용한다.
  예외: 연쇄 PR로 나누는 경우에는 9절에 따라 기존 커밋의 경계에서 브랜치를 나눈다.
- 기존 변경이 있으면 자동으로 이동·초기화·보관하지 않는다. 현재 변경의 소속과 안전한 진행 방법을 확인한다.
- 이미 진행 중인 브랜치에 규칙을 소급 적용하려고 임의로 이름을 바꾸지 않는다.
- `main`에서 직접 구현·커밋하지 않는다. 사용자가 명시적으로 요청한 경우만 예외로 한다.

새 브랜치를 만들 때는 원격 정보를 갱신하고 기준 커밋을 확인한다.
기존 브랜치를 계속 작업할 때는 임의로 리베이스하거나 기록을 다시 쓰지 않는다.

## 5. 구현과 검증

- 이슈 범위에 맞는 변경만 한다.
- 관련 문서를 함께 갱신하고, 가능한 범위에서 빌드·테스트·데이터 검증을 수행한다.
- 실기기나 Apple Intelligence가 필요한 검증은 실행 여부를 구분해 기록한다.
- 실행하지 않은 테스트는 통과했다고 쓰지 않는다.
- `.DS_Store`, 개인 설정, 인증 정보, 임시 결과물은 커밋에서 제외한다.
- 파일이 이미 추적 중이면 `.gitignore`만으로 제외되지 않으므로 추적 여부도 확인한다.

## 6. 커밋

### 형식

`[유형] 작업 내용 (#이슈번호)`

예: `[fix] 음식 분량 입력의 단위 해석 오류 개선 (#21)`

- 독립적으로 설명 가능한 변경 단위로 나눈다.
- 커밋 전 변경 내용과 스테이징된 파일을 확인한다.
- 필요한 파일만 경로를 지정해 스테이징한다. 관계없는 변경을 함께 넣지 않는다.
- `git diff --check`와 스테이징된 차이를 확인한다.
- 기존 커밋 수정이나 강제 푸시는 별도 요청 없이 하지 않는다.

## 7. 푸시 및 추적 브랜치

- 로컬 작업 브랜치와 같은 이름의 원격 브랜치로 푸시한다.
- 최초 푸시는 대상을 명시한다. 예: `git push -u origin 'fix/#21'`
- 이후에도 추적 대상이 `origin/fix/#21`인지 확인한다.
- 작업 브랜치가 `origin/main`을 추적하는 경우, 인자 없는 `git push`를 실행하지 않는다.
  같은 이름의 원격 브랜치로 명시적으로 푸시해 추적 대상을 설정한다.
- `#`가 포함된 브랜치 이름은 명령에서 따옴표로 감싼다.
- 사용자가 요청하지 않은 원격 저장소나 브랜치로 푸시하지 않는다.

## 8. PR

- 동일한 작업 브랜치의 열린 PR이 있으면 중복 생성하지 않는다.
- 기본 대상은 `main`이며, 실제 기본 브랜치가 다르면 그 브랜치를 사용한다.
  예외: 연쇄 PR은 9절에 따라 바로 앞 PR의 브랜치를 대상으로 한다.
- 제목은 `[유형] 작업 목적`으로 작성하고 이슈 번호를 붙이지 않는다. 이슈는 본문의 `Closes`·`Refs`로 연결한다.
  예: `[fix] AI 식사 입력의 음식·분량 매칭 개선과 회귀 테스트 도입`
- 기본적으로 초안 PR로 생성한다.
- 생성 전 대상 브랜치와의 전체 차이를 확인하고 무관한 커밋이 섞이지 않았는지 점검한다.
- 저장소의 PR 템플릿을 우선 사용한다. 현재 템플릿의 두 섹션을 유지하면서 검증 내용을 덧붙인다.
- 기존 `Resolved: #번호` 대신 GitHub 이슈 연결 키워드인 `Closes #번호`를 사용한다.
  이슈의 일부만 처리한 PR은 `Refs #번호`로 연결하고 자동 종료하지 않는다.

```markdown
## 🌴 작업한 브랜치
- `fix/#21` → `main`
- Closes #21

## ✅ 작업한 내용
- 실제 구현한 변경 사항

### 검증
- 실행한 검증과 결과
- 미실행 항목 및 이유

### 확인이 필요한 사항
- 실기기 확인이나 알려진 제한 사항이 있을 때만 작성
```

## 9. 연쇄 PR(큰 작업 분리)

한 브랜치에 쌓인 커밋이 많아 한 번에 검토하기 어려울 때 여러 PR로 나누는 방법이다.
사용자가 명시적으로 요청할 때만 적용한다.

### 브랜치 나누기

- 이미 쌓인 커밋은 기록을 다시 쓰지 않는다. 리베이스, 리셋, 강제 푸시로 커밋을 옮기거나 합치지 않는다.
- 검토 단위가 끝나는 경계 커밋을 정하고, 그 커밋에서 새 브랜치를 만든다.
  예: `git branch 'fix/#21-1' <경계 커밋>`
- 이름은 `유형/#이슈번호-순번`으로 한다. 예: `fix/#21-1`, `fix/#21-2`
- 마지막 브랜치는 원래 작업 브랜치 이름을 유지한다. 예: `fix/#21-1` → `fix/#21-2` → `fix/#21`
- 나누기 전에 경계 커밋 목록과 각 브랜치에 들어갈 커밋 범위를 사용자에게 보여주고 확인한다.

### PR 대상

- 첫 PR의 대상은 `main`이다.
- 이후 PR의 대상은 바로 앞 PR의 브랜치다. 예: `fix/#21-2` → `fix/#21-1`, `fix/#21` → `fix/#21-2`
- 앞 PR이 머지되면 다음 PR의 대상을 `main`으로 바꾼다. 대상을 바꾼 뒤 전체 차이에 앞 PR의 커밋이
  다시 나타나지 않는지 확인한다.

### 이슈 연결

- 마지막 PR에만 `Closes #번호`를 쓰고, 앞 PR에는 `Refs #번호`를 쓴다.
- `Closes`는 PR이 기본 브랜치로 머지될 때만 이슈를 닫는다. 앞 PR의 브랜치를 대상으로 머지된 PR의
  `Closes`는 이슈를 닫지 않으므로, 마지막 PR이 `main`으로 머지되는지 확인한다.

### 머지 방식

- 연쇄 PR 묶음은 squash가 아니라 merge commit으로 머지한다. squash하면 앞 PR의 커밋이 다른 커밋으로
  `main`에 들어가, 다음 PR의 차이에 이미 머지된 변경이 다시 나타난다.
- 각 PR 설명에 연쇄 순서(몇 번째 PR인지, 앞뒤 PR 링크)와 "merge commit으로 머지"를 적는다.

## 10. 완료 보고

완료 후 이슈 번호·링크, 작업 브랜치, 커밋, 푸시 여부, PR 링크와 검증 결과를 간단히 알린다.
생성한 PR을 채팅에 연결하는 도구가 있으면 함께 연결한다.
인증·권한·검증 실패로 중단했다면 완료된 단계와 남은 작업을 명확하게 구분한다.

## 11. 금지 사항

- 별도 요청 없는 PR 머지, 강제 푸시, 원격 브랜치 삭제
- 사용자의 변경 삭제나 파괴적인 초기화
- 기본 브랜치에 작업 브랜치 내용을 잘못 푸시하는 행위
- 비밀 키·개인 파일·무관한 변경의 커밋
- 실패한 작업이나 실행하지 않은 검증을 완료로 보고하는 행위
