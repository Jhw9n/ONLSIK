# 자연어 식사 입력

Figma `2213:894`(기본), `2213:533`(입력 중)의 레이아웃을 기준으로 구현했습니다.

## 현재 범위

- 기록 화면의 식사 추가 버튼에서 `MealEntryPresentation`이 OS 버전, `SystemLanguageModel.default.availability`, 한국어 지원 여부를 먼저 확인합니다. 사용 가능하면 `MealEntryView`, 아니면 이유 안내와 함께 `FoodSearchView`를 직접 표시합니다. 선택한 날짜·식사 종류·저장 후 갱신은 양쪽 모두 유지합니다.
- 프로젝트와 앱 타깃의 Debug/Release 배포 버전은 iOS 18.0입니다. AI 기능만 iOS 26 및 Apple Intelligence 사용 가능 상태를 요구합니다. 기기 미지원·설정 꺼짐·모델 준비 중·언어 미지원에서는 직접 검색을 사용할 수 있습니다. 한 번 들어간 화면의 모드는 유지하여 검색·수량 입력 도중 화면이 교체되지 않게 하고, 다음 진입 시 다시 확인합니다. 분석 요청 직전의 지원 여부 검사도 유지합니다.
- 입력창에 초점을 두거나 내용이 있으면 테두리와 초록 그림자를 표시합니다. 공백만 입력하면 전송할 수 없습니다.
- 입력창은 한 줄 높이로 시작해 줄바꿈에 따라 최대 6줄까지 늘어나며 이후에는 입력 영역 안에서 스크롤합니다.
- 하단 기록하기 버튼은 항상 화면 하단에 두고, 추가 선택을 마쳐 유효한 확인 카드가 있을 때만 활성화합니다.
- 전송하면 키보드를 내리고 최근 식사 영역을 분석 중 → 추가 선택 또는 확인 카드로 교체합니다.
- 입력을 수정하면 기존 분석 및 결과를 무효화합니다. 이전 비동기 요청이 늦게 끝나도 새 결과를 덮어쓰지 않습니다.
- 최근 식사는 해당 사용자의 선택 날짜까지 최근 30일 기록을 날짜·식사 종류별로 묶어 중복을 제외한 3개를 표시합니다.
- 최근 식사를 선택하면 저장 전 분량을 확인하고 조정할 수 있습니다. 확인 버튼을 눌러야 해당 날짜·종류에 한 끼 전체를 저장합니다.
- 확인 카드 안에서 −/수량/＋로 양을 수정합니다. 줄·공기 등은 0.5씩, g·mL는 10씩 조절하고 가운데 숫자는 소수 둘째 자리까지 직접 입력할 수 있습니다. 입력 범위는 0.1~10,000이며 빈 값·잘못된 값일 때는 기록하기를 비활성화합니다.
- 예상 열량과 기록하기 버튼은 하단에 고정됩니다. 수량이 잘못된 동안에는 이전 열량 대신 `— kcal`를 표시합니다.
- 식사 입력이나 수량 수정으로 키보드가 올라오면 하단 고정 영역 위를 덮습니다. 버튼을 조건부로 제거하거나 키보드 위로 이동하지 않으며, 입력 내용은 별도의 스크롤 영역에서 키보드를 피합니다.
- 입력 영역 밖을 누르면 키보드를 닫습니다. 식사 입력·추가 설명·수량 입력 영역 안의 터치는 제외해 커서 이동과 입력을 유지합니다.
- 최근 식사는 저장된 분량을 그대로 사용합니다. 새 기록은 원래의 분량·영양값 근거를 내부적으로 유지합니다.
- 실제 분석에는 `AppleMealFoodInterpreter`의 Foundation Models를 사용합니다. 프리뷰 구현은 실제 앱에 주입하지 않습니다.

## 분석 흐름

1. 기기의 Apple Intelligence 사용 가능 여부와 한국어 지원을 확인합니다.
2. 입력한 식사의 음식 이름·브랜드를 구조화합니다. 수량은 후속 원문 검증에서 처리합니다. 한 번에 500자, 음식 8개까지 처리합니다.
3. 음식 이름이 원문에 나타나는 위치를 찾아 음식별 문구를 분리합니다. 한 줄·반 접시·두 조각·g·mL 등 명시된 수량은 원문에서 다시 읽고, 없는 수량은 1인분, 조금은 소량으로 표시합니다. 모델이 다른 음식의 단위를 옮겨 붙이거나 근거 문구에 없는 내용을 추가해도 사용하지 않습니다. 원문에 없는 음식, 중복 추출, 비정상 수량·단위는 거부합니다.
4. 기존 `FoodCatalogService`로 로컬 영양정보 DB를 검색합니다. 일반 음식을 우선하며, 명시된 브랜드와 g/mL 단위는 유지합니다.
5. 이름이 정확한 일반 음식은 바로 연결합니다. 유사 후보는 AI가 같은 음식의 작은 재료 차이인지 판단해 대표 후보를 연결합니다. 생재료와 조리 음식, 튀김 여부 등 중요한 차이를 무시하거나 이름 일부만 같은 음식을 연결하지 않도록 지시합니다. 이는 모델 판단이므로 실기기 품질 검증이 필요합니다.
6. 소스가 없는 스파게티·파스타는 소스를 질문합니다. 소스 원재료가 아닌 완성된 스파게티 후보를 보여줍니다. 그 외에도 식별에 중요한 정보가 부족할 때만 짧은 설명을 한 번 요청합니다. 다른 음식과 원래 수량은 질문을 거쳐도 보존됩니다.
7. 적절한 DB 후보가 없으면, 음식 이름 또는 사용자가 설명한 재료·조리법으로 식별 가능한 음식의 100g/100mL당 영양값을 추정합니다. 한 단위 분량은 별도의 요청에서 추정해 영양 기준량과 혼동하지 않도록 합니다. 추정의 기본 음식·재료가 해당 음식 이름 또는 추가 설명에 실제로 등장하고, DB 검색에서도 확인되는지 검사합니다. 모델이 모르는 메뉴에 임의의 재료를 붙여도 이 조건을 통과하지 않으면 설명을 요청합니다. 설명 후에도 추정할 수 없으면 저장하지 않습니다.
8. DB에 연결된 음식은 입력한 g/mL → 확인된 대표 분량 → 등록된 기본 추정량 → AI 분량 추정 순서로 적용합니다. 기본 추정량도 근거는 `estimated`로 기록하며, 검증된 대표 분량으로 취급하지 않습니다. 단위가 다르면 무게와 용량을 임의로 환산하지 않습니다. 추정 영양값도 입력한 수량에 맞춰 환산합니다.
9. 사용자가 확인 카드의 수량을 조절하고 기록하기를 누른 뒤에만 한 끼 전체를 저장합니다.

**DB 영양값을 우선하고, 적절한 후보가 없을 때만 AI 영양 추정을 사용합니다.** 모델의 구조화된 응답은 실제 영양값의 정확성을 보장하지 않습니다. 브랜드·실제 조리법·국물 섭취 차이까지 재현하는 분석은 아니며, 특정 제품의 표시 영양값을 대신하지 않습니다.

대표 분량이 없는 음식은 조리 상태와 단위를 바탕으로 한 단위의 양을 추정합니다. `단무지 조금`처럼 소량인 경우에는 조절하기 쉬운 g/mL로 표시합니다. 확인 카드에는 `약 200g`처럼 무게만 표시하고, 하단의 `예상 열량`과 공통 안내 문구를 유지합니다. 음식마다 `AI 추정`을 반복해서 붙이지 않습니다.

`반찬 조금`처럼 음식 종류가 특정되지 않은 경우에는 DB의 임의 반찬이나 10g으로 확정하지 않고 이름을 확인합니다. AI가 원문의 `반찬`을 누락해도 해당 표현을 별도로 분리해 `조금`이 앞의 국밥 분량에 붙지 않도록 합니다. `반찬은 안 먹었어`처럼 직접적인 부정 표현은 제외합니다. 답변에 명시한 수량이 있으면 우선하고, 이름만 답하면 원래의 `조금`을 유지합니다. 먼저 분석한 다른 음식은 다시 계산하지 않습니다.

반찬 답변의 여러 음식은 각각 분석하며 반찬이라는 맥락을 유지합니다. 조리된 일반 음식 후보가 있으면 건조 원재료나 브랜드 제품보다 먼저 검토합니다. 젓갈 이름은 `오징어젓갈`과 `오징어 젓갈`처럼 띄어쓰기가 달라도 동일한 검색어로 처리합니다. 반찬 확인 입력창에는 재료·조리법 대신 반찬 이름을 적도록 안내합니다.

후보 매칭 AI는 질문 문장을 생성하지 않고 후보 번호와 필요한 확인 종류(`none`, `sauce`, `preparation`, `ingredients`)만 반환합니다. 후보를 선택한 경우 추가 질문을 하지 않으며, 후보가 없고 필수 정보가 부족할 때만 앱이 관리하는 짧은 질문을 표시합니다. DB 열량은 매칭 질문 생성에 제공하지 않습니다. 모델이 만든 영양 설명·제품 비교·자유 대화를 질문 제목으로 노출하는 경로는 없습니다.

분량 추정에서는 한 단위의 전체 구성을 먼저 기술하고 무게/용량을 답하도록 합니다. 국밥은 밥·건더기·국물을 포함하며, DB의 100mL 기준량을 기본 1인분으로 쓰지 않습니다. 국밥·덮밥·면류 등 한 끼 음식의 인분/그릇/접시/공기 추정값은 200~2,000 범위를 벗어나면 한 번 재확인하고, 여전히 비정상이면 분량 입력을 안내합니다. 이 범위는 잘못된 출력 탐지용의 보수적 규칙으로, 권장 섭취량이나 특정 음식의 검증된 제공량이 아닙니다. 경계값으로 강제 보정하지 않으며 명시적으로 입력한 g/mL와 반 그릇·두 그릇의 배수 계산에는 적용하지 않습니다.

분량 근거와 영양값 근거(DB 직접 연결·유사 음식·추정), 참조한 DB 음식 또는 추정 재료는 기록 내부에 저장합니다. 기존 기록은 새 메타데이터가 비어 있어도 읽을 수 있습니다.

추정 영양값은 유한한 수인지, 음수가 아닌지, 100g당 영양소 합계와 열량·영양소 간 계산이 크게 어긋나지 않는지 검사합니다. 그릇·접시 등이 1g으로 나오는 명백한 분량 오류도 차단합니다. 이 검증은 비정상 출력을 거르는 장치일 뿐 영양학적 정확성의 인증은 아닙니다. 검증에 실패하면 임의로 수치를 보정해서 저장하지 않습니다.

수량 해석은 명시적인 숫자·단위와 한/두/반 등의 표현을 우선합니다. 여러 사람이 나눠 먹은 비율, 남긴 양을 빼는 계산 등 복합 표현은 현재 정확하게 보장하지 않으므로 확인 카드에서 실제 먹은 양을 조절해야 합니다.

기본 분석기는 매 요청마다 새 세션을 사용하며, 앱에서 식사 원문을 서버로 전송하거나 로그로 남기지 않습니다. 질문 이후에는 해당 식사의 선택·추가 설명·나머지 음식만 이어서 처리합니다.

## 일상적인 음식 이름 처리

대표 목록과 검색 확장 방식은 [대표 음식과 검색 보완](FoodReferences.md)을 따릅니다. 등록된 43종은 원본 레코드를 고정하고, 나머지는 기존 DB 검색과 최대 1회의 AI 검색어 재작성으로 후보를 검토합니다. 별칭은 코드 내부가 아닌 `FoodReferences.json`에서 관리합니다. 유사 철자 검색 결과나 AI가 새로 제안한 검색어는 자동 정답으로 연결하지 않습니다.

### 정식·세트와 숟가락 입력

- `고등어정식`, `햄버거 세트` 등은 AI 추출 전에 구성 확인 화면을 표시합니다. 세트를 임의로 음식·반찬으로 분해하지 않습니다. 사용자가 이번 식사 전체의 음식과 먹은 양을 쉼표로 적도록 안내하고, 답변을 새 식사 목록으로 분석합니다. 원문에 별도로 쓴 음료도 답변에 포함하도록 안내하며 원문 음식과 답변을 합쳐 중복 계산하지 않습니다. 세트 자체를 다시 입력하면 구성을 다시 묻습니다.
- 답변에서 사용자가 실제 먹은 양을 지정하므로 원문의 `정식 반`을 답변 전체에 다시 곱하지 않습니다. 예: `밥 반 공기, 고등어구이 반 접시`는 각각 0.5로 처리합니다.
- `회덮밥 한숟가락`, `두 숟갈`, `반 수저`는 음식명과 수량을 분리하고 `숟가락` 단위로 통일합니다. 음식 종류에 따라 한 숟가락 무게를 추정하며 1인분 분량을 대신 쓰지 않습니다. 숟가락/큰술 1~50, 작은술 0.5~20 범위 검사는 명백한 오류 탐지용이며 실측 제공량이 아닙니다. AI 추정이 범위를 벗어나면 재확인 후 실패 처리하며 경계값으로 보정하지 않습니다.

- `순찌`는 `순두부찌개`, `공기밥·흰밥·흰쌀밥·백미밥·밥`은 `쌀밥`으로 연결합니다. 추출용 문구만 정규화하며 사용자의 입력창과 원문은 바꾸지 않습니다. 모델이 정식 이름을 반환해도 원문의 등록된 별칭 위치를 찾아 수량을 읽습니다.
- 별칭은 등록된 이름만 허용합니다. `볶음밥` 속의 `밥`, `밥버거` 등을 쌀밥으로 바꾸거나 명시한 해물 등의 재료를 제거하지 않습니다.
- `공기밥 하나·둘·두 개`는 각각 1·2·2공기로, `순찌 절반`은 0.5인분으로 처리합니다. 명시한 g/mL는 유지합니다.
- 브랜드를 명시하지 않은 음식은 같은 요리명의 일반 조리 음식 후보가 있으면 가공식품의 정확한 이름 일치보다 우선합니다. 정확한 일반 음식도 AI 검토용 8개 제한 전에 전체 호환 후보에서 찾습니다.
- 재료를 따로 지정하지 않은 `순두부찌개`는 단위가 호환되는 일반 조리 음식 `순두부찌개 모듬`을 참조합니다. 이 참조가 실제 DB에 있을 때만 재료 질문 없이 연결하며, 유사 음식 근거와 원본 출처를 기록합니다. 해물 등 명시한 종류나 추가 설명, 브랜드 제품에는 이 기본값을 강제하지 않습니다. 분량은 여전히 별도로 추정하며 g과 mL를 서로 바꾸지 않습니다.
