# 식사 분량 검증 (#21)

## 카레와 반찬 소량

- 식약처 음식 영양성분 자료의 카레라이스 1인분 500g을 그릇 단위로 적용한다. 현재 DB의 카레라이스 108kcal/100g을 유지하므로 한 그릇은 540kcal다. 검색 요약의 열량에 맞추기 위해 영양값을 수정하지 않는다.
- 브랜드 없는 `카레`는 기본적으로 카레라이스로 해석하되, 밥 없이/밥 제외/소스만 표현이나 별도로 입력된 쌀밥이 있으면 카레소스로 해석해 밥 중복 계산을 피한다.
- 일반 `김치`는 배추김치를 기본 후보로 사용한다.
- `조금`, `약간`, `종지`와 함께 입력한 김치·깍두기·단무지는 30g, 나물 및 등록된 무침 반찬은 30g, 젓갈·멸치볶음은 10g을 앱의 **소량 추정 기본값**으로 사용한다. 공식 1회 분량이나 실측값을 의미하지 않는다.
- 출력은 작은 반찬 1접시를 기준으로 조절하며 `.estimated`로 저장한다. 직접 입력한 g/mL는 항상 우선한다. 김치볶음밥·김치찌개에 반찬 소량 기본값을 적용하지 않는다.
- 참고: 정부 식생활 길라잡이의 김치·단무지 1회 분량은 40g이다. 앱의 “조금” 30g은 이와 구분되는 제품 설계상 추정값이다.

## 11월 5일 생활 단위 보완

- `아사이시오라멘`처럼 알려진 메뉴 `야사이시오라멘`과 길이가 같고 한 글자가 다른 단독 입력은 교정 후보를 확인한다. 자동 치환하지 않으며 모든 오타를 지원하는 것은 아니다.
- 브랜드 없는 라멘은 기존 출처 있는 우동 1그릇 700g을 **유사 분량**으로 제안한다. 라멘의 검증된 대표량이 아니므로 차이를 안내하고 동의를 받은 뒤 적용한다. 수량은 그릇으로 조절한다.
- 브랜드 없는 너겟의 개/조각은 맥도날드 공식 영양정보의 맥너겟 4조각 64g(https://www.mcdonalds.co.kr/eng/menu/information/nutrition, 2026-11-05 확인)을 참고하여 낱개 16g을 제안한다. 다른 제품에 동일한 실제 중량을 보장하지 않으며 확인 후 적용한다.
- 두 기준 모두 `.estimated`로 보존하고 영양값은 선택한 DB 음식에서 계산한다. 명시적인 g/mL 입력은 제안을 거치지 않고 원래 양을 보존한다.
- 이 경로에서는 분량 모델을 다시 호출하거나 g 입력을 강제하지 않는다. 다른 음식의 실패 경로도 아래 11월 6일 변경으로 생활 단위 확인을 사용한다.
- 아래 초기 분량 실패 테스트 기록과 달리, 위 조건에 해당하는 라멘·너겟은 이제 생활 단위 기준 확인을 우선한다.

## 낱개와 1인분 구분

- 영양 DB의 100g/100mL는 영양값의 기준량이며 낱개 또는 1인분의 양이 아니다.
- 모델은 요청한 한 단위의 양만 추정하며 앱이 사용자가 입력한 개수를 곱한다.
- 너겟/너깃/너켓의 `개`, `조각` 추정은 1~60g 범위만 허용한다. 이는 명백한 봉지·접시 단위 혼동을 거르기 위한 앱의 안전 범위이며, 공식 대표 분량이나 정확도를 보장하는 기준이 아니다. 범위 안의 값도 실기기 검증이 필요하다.
- 이 범위는 다른 음식의 `개`에 적용하지 않는다. 사용자가 직접 입력한 g/mL도 이 추정 범위로 제한하지 않는다.
- 모델은 잘못된 추정을 재확인하며, 끝내 분량을 판단하지 못하면 생활 단위 선택이나 짧은 양 표현을 요청한다. 임의의 값으로 잘라 맞추지 않는다.
- 추가로 입력한 양은 원래 개수와 다시 곱하지 않는다. 이전에 처리한 음식과 아직 처리하지 않은 음식은 유지한다.
- 숫자만 답하면 화면에 안내한 생활 단위를 사용한다. 음수, 0, 10,000 초과, 해석할 수 없는 문장은 재입력을 안내한다. 사용자가 자발적으로 입력한 g/mL는 허용하되 서로 임의 환산하지 않는다.

## 11월 6일 무게 입력 강제 제거

- `돼지갈비 한 국자`, `두 조각`, `반 공기`, `한 컵 반`, `두 종지`를 수량과 생활 단위로 분리한다. 직접 입력한 g/mL가 있으면 그 양을 우선한다.
- 음식 이름만 입력하면 1인분을 기본으로 처리한다. 출처 있는 대표 분량과 기존 음식별 기준을 우선하고, 없는 경우에만 음식의 조리 상태에 맞춰 모델이 한 단위 분량을 추정한다. 모든 음식을 100g으로 채우지 않는다.
- 내부 추정에 국자·종지를 추가하고, 반찬 종지는 기존 소량 기준으로 계산한다. 국자 10~250, 종지 5~100의 수치 검사는 모델의 명백한 단위 혼동을 거르는 앱의 안전 범위이지 공식 대표 중량이나 정확도 보장이 아니다. g/mL의 차이를 유지한다.
- 일반 음식의 분량 확인은 `0.5인분 / 1인분 / 1.5인분` 또는 음식에 맞는 그릇·개·컵 등의 버튼을 먼저 보여준다. 국·찜·갈비 등에는 국자 선택지를 제공한다. 다른 양은 짧게 직접 적을 수 있고 숫자만 입력하면 안내한 생활 단위를 적용한다.
- 사용자가 답한 뒤에도 환산 근거를 얻지 못하면 같은 질문을 반복하거나 임의 중량을 확정하지 않는다. 다른 분량 표현이나 음식 종류를 알려 달라는 오류를 표시한다. 영양 추정 경로에서 발생한 분량 실패에도 같은 정책을 적용한다.
- `조금`은 내부 중량으로 계산하되 결과 조절은 작은 접시 단위로 유지한다. 직접 무게를 입력한 경우에만 무게 단위 조절을 사용한다. 검증된 포장제품은 기존 포장 개수·규격 정책을 유지한다.
- 임시 Swift 모의 검사에서 국자·조각·종지·공기·컵·명시적 g/mL 해석, 대표량 우선, 국자 선택 후 재계산, 잘못된 답변, 반복 질문 방지, 단위 불일치 거부, 앞뒤 음식 보존, DB 미매칭 음식의 분량 오류 처리를 확인했다. 모델의 실기기 환산 정확도는 별도 확인이 필요하다.

## 검증

### 11월 15일 소주·냉동삼겹살·숯불주꾸미

- `병`을 수량 해석 단위에 추가했습니다. `소주 한병`, `반 병`, `한 병 반`, `두 잔`을 원문에서 읽고 후보 선택 이후에도 보존합니다. 소주의 병·잔을 인분으로 바꾸지 않습니다.
- 통칭 `소주`는 무작위 원재료성 소주(25도 등)나 모델의 분량 추정을 사용하지 않습니다. (2026-11-15 변경) 제품 확인 질문 없이 `Resource/Data/DrinkReferences.json`에 지정한 대표 항목(좋은데이 `P115-102020100-0013`, 100mL당 89kcal)으로 바로 기록하고, 다른 제품은 기록 화면에서 바꿉니다. 특정 도수를 명시하면 대표값으로 임의 대체하지 않고 제품명을 묻습니다.
- 병은 제조사 자료의 360mL 규격([무학](https://www.muhak.co.kr/product/goodday/), [롯데칠성](https://company.lottechilsung.co.kr/kor/brand/saero/contentsid/970/index.do), 2026-11-15 확인)을 사용합니다. 다른 용량은 사용자가 적은 mL/L를 우선합니다. 잔은 [국가암정보센터의 소주 잔 50mL 예시](https://www.cancer.go.kr/lay1/S1T231C233/contents.do)를 참고하며 실제 잔의 크기는 다를 수 있어 분량 근거를 추정으로 남깁니다. 소주를 인분·g으로 추정하거나 g과 mL를 임의로 환산하지 않습니다.
- 양이 생략된 소주는 표의 기본 용기(`1병 · 360mL`)로 기록하며 기록 화면에서 조절할 수 있습니다. 사용자가 `2인분`처럼 모호한 단위를 명시한 경우 이를 2병으로 바꾸지 않고 병·잔 단위의 확인을 요청합니다. 검증되지 않은 포장제품 전체에 이 규격을 적용하지 않습니다.
- 음식 이름 앞의 상태·조리 수식어(`냉동`·`냉장`·`생`·`숯불`·`직화`)는 코드가 아닌 `Resource/Data/FoodModifiers.json`에서 관리합니다. 이름 그대로 일반 음식을 찾지 못하면 수식어를 뗀 이름으로 다시 검색하고(예: `냉동만두` → `만두`), 결과는 `비슷한 음식 기준으로 기록할까요?` 확인 질문으로 보여 줍니다. 냉동·냉장은 보관 상태라 분류 선호가 없고, `생`은 원재료 `생것`을 먼저 봅니다. `숯불`·`직화`는 ① 뗀 이름과 같은 항목 ② `재료+구이` 조리 음식(`preferNameSuffixes`) ③ 원재료 `구운것` → `생것`(`rawStates`) ④ 그 밖 순서이고, `국·탕·조림·전·찜·볶음`으로 끝나는 조리 음식(`avoidNameSuffixes`)은 맨 뒤입니다. 뗀 이름 자체가 그 끝말로 끝나면(`직화낙지볶음` → `낙지볶음`) 뒤로 미루지 않고, 입력한 이름과 정확히 같은 항목은 항상 먼저입니다. 원재료로 연결되면 `rawDisplayText`("양념과 기름은 반영하지 않아요")를 보여 주고, 원재료에는 근거 있는 1인분이 없어 분량은 모델 추정이며 기록에 `AI 추정`으로 표시합니다. `생강`·`생선`처럼 수식어로 시작하는 음식 이름은 `keepWords`로 떼지 않습니다. 냉동이라는 표현만으로 포장제품으로 분류하지 않습니다.
- 삼겹살(`냉동`·`생`·`숯불` 등 수식어와 `냉삼` 포함) 1인분은 조리 전 생고기 170g을 농진청 `돼지고기, 삼겹살, 생것`(100g당 372kcal) 영양값으로 계산합니다(2026-11-15 결정, 약 632kcal). 값은 `FoodReferences.json`의 `삼겹살` 항목(`category: 원재료성 식품`, `estimatedPortions.인분: 170`)에서만 관리합니다. 굽는 동안 빠지는 기름은 반영하지 않습니다. 메뉴 이름이 `삼겹살구이`인 경우는 조리된 음식 영양값(100g당 467kcal)에 1인분 조리 후 130g을 씁니다(2026-11-15 결정: 생고기 170g에 대응하는 값, 약 607kcal). 이전 1접시 200g(대한당뇨병학회 인용 식약처 외식 자료)은 쓰지 않습니다.
- `쭈꾸미`·`주꾸미`를 같은 철자로 검색하고 원문도 양방향으로 찾습니다. `숯불주꾸미`·`직화주꾸미`는 위 수식어 규칙으로 `주꾸미`를 다시 찾아 조리된 `주꾸미볶음`을 먼저 제시합니다. 이전의 메뉴 이름 목록(코드)은 제거했습니다.
- 이 수정은 대표 자료 연결과 단위 처리 보완이며, 미등록 음식 전체 또는 식당별 실제 분량·도수·레시피의 정확도를 보장하지 않습니다.
- 실제 SQLite와 분량 추정을 실패시키는 모의 모델로 병/반 병/여러 병/잔/mL 보존, 소주 인분·컵 표현의 생활 단위 재확인, 특정 도수 자동 대체 차단, 냉동삼겹살·숯불주꾸미 후보 확인 및 대표 분량 적용, 앞뒤 음식 유지 여부를 검증했습니다. 실기기의 실제 모델 응답은 별도 확인이 필요합니다.

### 11월 6일 실기기 실패 후 보완

- `돼지갈비 한국자`와 `돼지갈비 한 국자`처럼 음식명 뒤에 수량이 붙은 단일 입력은, 음식명이 등록된 기준 또는 DB의 정확한 이름과 일치할 때 모델 추출 없이 분리한다. 부정·대체 표현, 여러 음식, 미등록 이름은 이 경로로 확정하지 않는다.
- 일반 `돼지갈비` 입력은 같은 이름의 가공식품으로 확정하지 않고 DB의 g 기준 조리 음식 중 구이·찜을 확인한다. 수량과 국자 단위는 유지한다. 현재 DB에서 돼지갈비구이 간장과 돼지갈비찜 후보를 실제로 조회해 검사했다.
- 국자 환산에 실패하면 같은 국자를 다시 선택시켜 동일한 모델 호출을 반복하지 않는다. 대표 분량이 있으면 그 기준을 제시하고, 없으면 일반 1인분 추정을 한 번 시도한다. 계산 가능한 기준을 확보한 경우에만 0.5/1/1.5단위 선택지를 표시하고, 선택 시 저장해 둔 환산값을 사용한다. 국자를 자동으로 반 인분 등으로 바꾸지 않는다.
- 일반 1인분도 추정하지 못하면 값을 만들거나 계산 불가능한 선택지를 표시하지 않는다. 오류는 밝은 배경 위 진한 글자와 경고 아이콘으로 표시한다. 입력칸 번호는 크기와 대비를 높이고 포커스 테두리를 추가했다.
- 실제 DB와 추출 실패·국자 추정 실패를 강제한 모의 모델로 붙임/띄어쓰기 동일 처리, 조리 음식 후보 확인, 대표량 및 추정량 선택 후 모델 재호출 없음, 명시적 g 보존, 미등록 음식·부정 표현 차단을 확인했다. 이는 실제 Foundation Models가 국자를 정확하게 환산한다는 보장은 아니다.

### 줄별 식사 입력

- 한 카드 안에서 음식별 입력칸을 제공한다. 엔터 또는 `음식 추가`는 다음 빈 칸으로 이동하거나 새 칸을 추가한다. 최대 8줄이며 빈 칸은 분석하지 않는다. 여러 줄을 붙여넣으면 칸으로 분리하되 8줄을 넘으면 내용을 잘라 버리지 않고 안내한다.
- `분석하기`를 누르면 채워진 줄을 순서대로 분석한다. 한 칸에 여러 음식이 있으면 기존 분석기가 처리할 수 있으며 강제로 하나로 합치거나 버리지 않는다.
- 결과를 줄 ID별로 보관한다. 수정·삭제한 줄의 결과만 무효화하고 다른 줄의 성공 결과, 수량 수정, 음식 제외 상태는 보존한다. 추가 질문은 해당 줄에 연결하며 답변 후 나머지 줄을 이어서 처리한다. 미해결 줄이 있으면 저장할 수 없다.
- 음식 검색·분석 실패 시 해당 줄 아래에 원래 오류와 `여러 음식을 적었다면 한 줄씩 나눠주세요.`를 표시한다. 기기 미지원·분량 확인·입력 길이 제한 오류에는 이 문구를 추가하지 않는다.
- 임시 모의 분석기 회귀 검사로 줄 추가·삭제, 빈 줄 제외, 여러 줄 붙여넣기, 8줄/500자 제한, 실패 후 재시도, 질문 답변 재시도, 성공 결과 보존, 수량·제외 상태 유지, 최근 식사 재사용, 입력 수정 시 취소, 시간 초과 뒤 오래된 응답 무시를 검증했다.
- 실제 기기에서는 한국어 입력 중 엔터로 다음 칸 이동·키보드 유지, 긴 입력의 가로 스크롤, 8번째 입력칸 접근, 바깥 터치로 키보드 닫기, 키보드 아래 기록하기 버튼 위치를 확인한다. 모의 검증은 온디바이스 모델의 실제 응답이나 키보드 동작을 검증한 것이 아니다.

### 쉼표로 나열한 음식명

- `라면볶이, 계란빵, 참치김치김밥`처럼 수량이나 문장 없이 나열한 2~8개 이름이 모두 등록된 별칭 또는 DB의 정확한 음식명과 일치하면, 이름 추출 모델을 거치지 않고 원문 순서대로 처리한다. 복합 음식명을 재료로 분해하지 않는다.
- 이 확인은 음식명 인식일 뿐 제품·분량·영양값의 확정이 아니다. 제품 확인과 분량 검증, 계란빵 의심 데이터 제외는 그대로 유지한다.
- 미등록 이름, 부정 표현, 수량이 포함된 문장, 빈 목록 항목은 기존 자연어 분석 경로로 보낸다. 일부 항목만 인정하고 나머지를 버리지 않는다.
- 모델이 `계란빵`을 `달걀빵`으로 반환하는 경우 원문에 대응시키고 원래 표기를 보존한다. 다른 재료나 브랜드를 임의로 추가하는 것은 허용하지 않는다.
- 실제 DB와 이름 추출을 실패시키는 모의 모델로 첨부 문장이 제품 확인 단계에 도달하고, 제품 선택 뒤 455kcal와 나머지 두 음식이 보존됨을 확인했다. 실기기의 Foundation Models 응답 자체를 재현한 검증은 아니므로 후속 음식의 매칭·분량은 추가 확인이 필요하다.

### 수량 계산

- 일반 계란빵은 외부 출처의 개당 참고값을 별도로 저장하며, 단위 생략 시 1개를 제안한다. 출처와 약 80g 환산의 한계는 `Docs/PackagedFoods.md`에 명시했다.
- 추출 모델과 영양 추정 모델을 실패시키는 모의 구현에서도 `계란빵`, `계란빵 2개`, `계란빵 반개`, `달걀빵 반개`, `계란빵 60g`은 추가 질문 없이 각각 처리된다. 브랜드·추가 재료·부정 표현을 단순 계란빵으로 바꾸지 않는다.
- 라면볶이 제품 선택 뒤에도 계란빵 1개가 보존된다. 다음 음식인 참치김치김밥의 분량 확인 여부는 별도이며, 식사 전체의 모든 질문을 없애는 변경은 아니다.

초기 전체 무게 확인 방식의 임시 Swift 회귀 점검에서는 다음을 확인했다. 현재 질문 UI와 단위 생략 처리는 위 11월 6일 정책으로 대체되었다.

- 모델이 너겟 한 개를 200g으로 반환하면 2개 400g으로 확정하지 않고 전체 양을 질문한다.
- 전체 양에 40g을 답하면 40g으로 기록하며 모델을 다시 호출하지 않는다.
- 모델이 한 개 20g을 반환하면 2개는 40g으로 계산한다.
- 명시적으로 입력한 너겟 400g은 그대로 보존한다.
- 단위 불일치와 잘못된 숫자는 질문 상태를 유지한다.
- 앞서 처리한 음식은 전체 양 확인 후에도 유지된다.

실기기에서는 `치킨버거, 치킨너겟 2개, 콜라, 감자튀김`을 반복 입력하여 추정 분량과 질문 이후 나머지 음식 처리를 확인한다.

## 남은 범위

### 외래어 메뉴 검색 보완

- 현재 DB에는 `야사이시오라멘`이 없고 `라멘 시오라멘`이 있다. 두 음식을 동일한 메뉴로 취급하지 않는다.
- `야사이시오라멘`, `야채시오라멘`, `채소시오라멘` 단독 입력(선택적 수량 포함)은 모델 추출 실패에 의존하지 않고 해석한다. 부정 표현, 브랜드, 여러 음식이 섞인 문장은 이 단축 경로를 사용하지 않는다.
- 정확한 메뉴가 없으면 브랜드 없는 조리 음식 `시오라멘` 후보를 검색하고, 토핑 차이가 있음을 안내한 뒤 사용자가 선택해야 진행한다. 입력한 수량과 나머지 음식은 유지한다.
- 복합 문장의 외래어 메뉴는 모델에 원문 이름을 보존하도록 지시하지만 실기기에서 추가 검증해야 한다. 이 변경은 모든 외래어를 번역하는 일반적인 해결책이 아니다.

이번 변경은 DB에 연결된 음식의 낱개 추정 및 분량 확인 흐름에 집중한다. DB 미매칭 음식의 영양 추정 실패, 라멘의 기본 분량, 세트/외래어 메뉴 인식 정확도는 별도 검증·개선 대상이다.

### 11월 15일 술·음료 용기 단위 표

- 용기 단위(소주병 360mL·소주잔 50mL, 캔 355mL, 맥주병 500mL, 막걸리병 750mL)와 술별 대표 DB 항목을 코드가 아닌 `Resource/Data/DrinkReferences.json`에서 관리합니다. 소주 전용 코드는 이 표로 합쳤습니다.
- 맥주(`P115-104010400-0008`, 100mL당 53kcal)·막걸리(`P115-101010100-0007`, 100mL당 56kcal)의 대표 항목은 브랜드 없는 식약처 mL 기준 항목입니다. 같은 이름의 다른 열량 항목이 있어 참고값입니다.
- `캔`을 수량 단위로 읽습니다. 표에 없는 용기(예: 맥주 잔)는 기존 흐름(모델 추정 + 타당성 검사)을 따르며, 술은 mL 기준과 표의 용기별 허용 범위(`plausibleMilliliters`)를 벗어난 추정을 받지 않습니다.
- 캔 355mL·맥주병 500mL·막걸리병 750mL은 시판 표준 규격으로 정한 값이며 제조사별 출처는 아직 연결하지 않았습니다.

### 11월 15일 분량 상한과 고열량 확인

- 모델이 추정한 `인분`·`접시`·`그릇` 한 단위 분량은 1,000g(또는 mL) 미만만 받습니다. 1,000g 이상이면 추정값을 쓰지 않고 양을 다시 묻습니다(2026-11-15 결정: 원래 버그가 정확히 1,000g이었으므로 경계값도 거부). `공기`와 대표 분량표의 값은 이 상한과 별개입니다.
- 한 줄 열량이 1,000kcal를 넘으면 기록을 막지 않고 "이 양이 맞나요?"로 확인합니다. "그대로 기록" 또는 "절반으로 기록"을 고를 수 있고, 이후 기록 화면에서 조절합니다.

### 화면 문구와 내부 근거 분리

- 데이터 파일(`FoodReferences.json`, `FoodModifiers.json`, `DrinkReferences.json`)에서 화면에 보이는 문구는 `displayText`, 결정 날짜·출처 메모 같은 내부 근거는 `basisNote`에 둡니다. 앱은 `displayText`만 화면에 씁니다.
- `DisplayTextTests`가 데이터 파일의 모든 `displayText`와 실제 확인 질문 문구(제목·안내·선택지)에 날짜 형식, "결정", "내부 기준" 같은 내부 용어가 있으면 실패시킵니다.
- 기록에 저장되는 출처(`MealRecord.nutritionSource`)도 사용자에게 보여도 되는 문구만 씁니다. 술은 `DB 출처 · 대표 항목 영양값 기준 · 1병 360mL 기준`, 모델 추정은 `AI 영양 추정 · 재료`이며, 용기 용량의 내부 근거(`DrinkReferences.json`의 `source`)와 "대표값:" 같은 내부 표현은 저장하지 않습니다. 스키마는 바꾸지 않았고 이미 저장된 기록의 문자열은 그대로입니다. `StoredSourceTests`가 모든 식사 케이스와 참고값·포장제품 항목의 저장 출처를 검사합니다.

### 11월 17일 대표 분량 첫 단어 규칙의 한계

- DB 이름의 첫 단어(음식 + 변형, 예: `메밀국수 온면` → 메밀국수)로 대표 분량을 찾는 규칙은 공백으로만 나뉜 이름에만 씁니다. 쉼표가 있는 이름(`달걀, 가루`, `쫄면, 말린것`, `우동 건더기 스프, 삶은것` 등 19개)은 원재료의 상태·가공 이름이라 요리 분량을 붙이지 않고 수량을 묻습니다.
- 알려진 한계: 공백으로만 나뉜 `탕수육 소스`, `우동 건더기 스프`, `달걀 삶은것 흰자`, `달걀 삶은것 노른자` 4개는 여전히 첫 단어의 요리 분량(탕수육 1인분 200g, 우동 1그릇 700g, 계란 1개 50g)을 받습니다. 이 항목이 실제로 골라지는 사례는 아직 확인되지 않았습니다. 사례가 생기면 제외어 목록(데이터 파일)을 검토합니다.
